# ER Diagram Documentation

*Note: The actual Mermaid.js ER diagram code will be provided in the dedicated Diagrams section. This document explains the rationale behind the entities.*

## Core Entities Overview

### 1. `Universities`
Acts as the root tenant for B2B billing and coordinator access control.

### 2. `Users`
Central authentication table. Includes an `enum` for Role (STUDENT, COORDINATOR, ADMIN).
- **Students** belong to a `University`.
- **Coordinators** manage a `University`.

### 3. `Resumes`
A 1:1 relationship with `Users` (assuming one active resume at a time). Stores the parsed JSON data generated by DeepSeek and the calculated Resume Score (0-10).

### 4. `Interviews`
The core transactional table. A 1:N relationship from `Users`. Records the Target Company, Job Description text, and timestamps.

### 5. `Interview_Scores`
A 1:1 relationship with `Interviews`. Stores the final `career_readiness_score` and a JSONB payload containing the detailed dimension breakdown (e.g., Code Quality: 8, System Design: 6) generated by DeepSeek.

### 6. `Transcripts`
A 1:1 relationship with `Interviews`. Stores the sequential conversation array (Student: ..., AI: ...) as JSONB for rendering the side-by-side feedback view.

## Normalization & Denormalization Choices
- **Normalization:** Users are strictly normalized. Roles govern access.
- **Denormalization (JSONB):** Transcripts and Score Breakdowns are stored as JSONB rather than normalized relational tables (e.g., creating a table for `Utterances` or `Score_Dimensions`). This significantly reduces join complexity and read latency since transcripts are always retrieved as a single, complete document for rendering the frontend report.
